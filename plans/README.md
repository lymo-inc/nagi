## Backlog — vetted findings without a plan yet

Ordered roughly by leverage. IDs are stable; ask for "a plan for C-06" etc.

**Correctness (core)**
- **C-01b** `wf.start` enqueues the first steps *after* the run row commits
  (`runtime.ts` `startRunInternal` → `tryStartRun` then `dispatcher.advance`);
  a failure in between leaves a `running` run with nothing in the queue
  ("never scheduled" in the runbook). `startStaged` already does it inside
  the caller's tx via `bindQueueToTx`. Fix: same pattern for the plain path,
  or a "non-terminal run with no message/lease/timer" sweeper. Effort M (port change).
- **C-05** `startStaged` handles only a `dispatch` seed transition
  (`runtime.ts:595-603`); an entry step whose `when` is false yields `skip`
  and the run is stranded with no message. Effort S.
- **C-06** `foldRun` applies `flow.completed|failed|canceled` unconditionally
  (`state.ts:367-375`), so a cancel racing completion rewrites a finished run
  with no anomaly; `cancelRunRecursive` is check-then-act with no lock. Fix:
  fold guard + anomaly, then a store-level conditional cancel. Effort S/M.
- **C-07** `ctx.once()` re-executes when the memoized value is `null`
  (`idempotency.ts:23-31` uses `cached !== null`; `Json` includes `null`).
  Needs `Store.getOnce` to return presence (`{hit, value}`) in both adapters. Effort S–M.
- **C-08** `checkUpstream` treats a `canceled` upstream as `blocked` forever
  and `flowTermination` counts a canceled last step as success
  (`scheduler.ts:108-122, 194-206`). Reachable via an `operator.retry` whose
  abort wait times out. Needs a semantics decision. Effort M.
- **C-09** Claim/settle guards are not attempt-aware: a redelivered message
  for attempt N is admitted while N+1 runs (`exec/message.ts:155-168` has no
  attempt comparison; `claimStep` is keyed per attempt); Postgres
  `deleteLease` ignores `attempt` (`store.ts:873-882`) so a stale attempt's
  settle deletes the live lease; the claim token is never verified in SQL;
  `propagateToParent` is check-then-act (`exec/progression.ts:253-297`).
  One design plan: attempt-scoped delete, token-verified settle, conditional
  parent settle. Effort M–L.
- **C-10** In-memory adapter hygiene: leases never deleted on settle and
  `sweepLeases` breaks at `limit` before filtering expiry (`memory.ts:285-304`,
  so after ~100 settled steps the reference reaper reaps nothing); stream-hub
  channels never freed (`stream-hub.ts:98-162`); `pruneFacts` ignores
  `batchSize` (contract at `types.ts:713`) and `signalTimers`. Effort S.
- **C-11** Clock hygiene: `Date.now()` in `worker.ts:181` (`runUntilEmpty`)
  and `memory.ts` `describe`; `nagiRun` builds a second `InMemoryClock`
  (`runtime.ts:812`); cancel-watcher timer never cleared (`step-exec.ts:110-135`);
  `fire()` has no `.catch` (`worker.ts:245`). Effort S.

**Adapters**
- **A-02** Fact ordering: `fact_id` is a UUIDv7 with a purely random tail
  (`uuidv7.ts:26-33`) and `loadRunState` orders by it (`store.ts:330`), so two
  facts in the same millisecond fold in random order; the in-memory reference
  is insertion-ordered. Fix: `seq bigserial` column + `ORDER BY seq`, new
  migration, backfill by `fact_id`. Effort M, MED risk.
- **A-04** OTel step-span registry (`otel/src/context.ts:14`, process-global
  Map) is never drained for canceled steps because core fires no hook on

  `FlowHooks`, fire from both cancel branches, consume in otel. Effort M.
- **A-06** `queryRuns` orders by `(started_at DESC, run_id DESC)`
  (`store.ts:983`) with no matching index (`migrations.ts`). Effort S.
- **A-05** `maybeNotify` (`store.ts:895-900`) can reject a committed write;
  callers may retry and duplicate facts. Wrap and log. Effort S.
- **A-07** `pgmq inspect()` interpolates the queue name with `sql.raw`

## Direction (maintainer's call — design/spike plans on request)

- **DIR-01** `NagiConfig.trigger` and `Clock.schedule` are accepted but never
  called by the worker/dispatcher; `postgresTrigger` + `pg_notify` form a
  complete pair joined to nothing. Wire (poll races a NOTIFY wake) or delete
  both port members. Also moots the trigger's missing reconnect logic.
- **DIR-02** Ship a production `StreamTransport` (`InMemoryStore` is the only
  implementation; `nagi()` refuses to boot a streaming flow on the Postgres stack).
- **DIR-04** Enforce handler-step deadlines (issue #33): the lease-hold
  watchdog warns but nothing stops a wedged handler; `ctx.signal` is the
  existing abort path.
- **DIR-03** A testing kit: the in-memory adapters are public but
  `InMemoryClock` is real-time; a `FakeClock` + `runUntilIdle` would make
  timeout/retry flows unit-testable by consumers.
- **DIR-05 / DIR-06** Run-level event subscription (`wf.watch`) over the fact
  log; OTel metrics for the runbook's alert-by-grep instructions.

## Findings considered and rejected

- Local `.claude/settings.local.json` allow-listing `npm unpublish *` and
  `provenance: false` in the manifests: local tooling and a manual-release
  choice; not repo findings.
- Persisting flow inputs / error stacks in `workflow_run` and facts: inherent
  to a durable workflow engine; retention/redaction is a product policy, not a
  defect. (`pruneFacts keepSummary` leaving the run row is by design.)
- `bindQueueToTx` silently falling back for queues without `withTx`
  (`store.ts:1314-1318`): documented in-code as by design for the in-memory
  queue; a doc note for third-party queue authors is enough.
- `postgresTrigger` reconnect/listener leak: moot until DIR-01 decides whether
  the trigger path exists at all.
- Single-door exports, one-file `types.ts`, `RunState.facts`, sparse
  comments, per-package LICENSE, `patch` bumps in 0.1.x, `b.signal` requiring
  `timeoutMs`: all decided (RFC 0021 and maintainer policy).
- Type escape hatches (21 `as unknown as`, zero `@ts-ignore`): all at genuine
  adapter boundaries under a strict tsconfig; not worth touching.
- `pre-push` running the full suite: ~15 s total; fine.
- Changeset pre-mode "46 pending files": correct behavior of `changeset` pre mode.
- `moduleResolution: "Bundler"` in sources: safe, `test-types/` re-checks under `NodeNext`.
